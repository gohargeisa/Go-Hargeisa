# Go Hargeisa — Premium Splash Screen Redesign Report

**Date:** 2026-08-05
**Build:** Android versionCode `4`, versionName `1.3.0` (previous: versionCode 3 / 1.2.0). iOS project version untouched this pass (config-only changes, no Xcode toolchain available in this environment to bump/build it — see "What this pass does not cover").

## The problem

The previous native splash showed the app-icon glyph centered on a flat cream background — functional, but generic, with no relationship to the website's own Hero section, no animation, and no visual continuity into the homepage. The goal was an "Airbnb/Booking.com/Google Maps"-grade launch: a Hero-photo splash with a slow Ken Burns zoom, an animated logo + tagline sequence, and a seamless handoff into the real Home Hero with zero flicker.

## The hard constraint that shaped the design

Android's `Theme.SplashScreen` (via `androidx.core:core-splashscreen`, already correctly wired in this project) and iOS's `LaunchScreen.storyboard` are both OS-limited to **one static image** shown before any app code runs. Neither supports Ken Burns, sequenced fades, or reduced-motion detection. That's an Apple/Google platform limit, not an implementation gap — so this redesign uses the same two-layer pattern real hybrid/web-shell travel apps use:

- **Native layer** (brief, OS-mandated, static): a redesigned Hero-photo splash image — same `Theme.SplashScreen` + `drawable/splash.png` (Android) / `LaunchScreen.storyboard` + `Splash.imageset` (iOS) wiring as before, only the *image* changed.
- **Web layer** (full control): a new React/Framer Motion overlay that mounts as the homepage's JS boots, shows the *same* Hero photo with full animation, then fades away to reveal the real Hero underneath.

Because both layers render the same `hero-bg.png` through the same `HeroBackground` component with identical props, Next.js generates the identical `/_next/image` URL in both places — the browser's own image cache/decode makes the crossfade read as continuous rather than a scene change, which is what makes the hand-off actually seamless rather than just visually similar.

## Design decisions

- **Logo asset**: `public/images/logo.png` (1536×1024) was found — via row-by-row alpha sampling — to have "DISCOVER • EXPLORE • EXPERIENCE" baked into the raster as a separate pill, separated from the actual mark by a fully-transparent gap. A new `public/images/logo-mark.png` (768×418, generated by `scripts/generate-mobile-assets.mjs`'s new `getLogoMark()`) crops that out, keeping only the mark — which already has a soft golden glow baked in, satisfying "extremely subtle glow" for free. This is also the file the splash overlay's animated logo uses.
- **Light/dark mode**: `components/layout/theme-provider.tsx` sets `forcedTheme="light"` — the live app cannot enter dark mode in production. One splash treatment was built, not a speculative unreachable dark variant.
- **Ken Burns**: reuses the existing `animate-kenburns` Tailwind keyframe (`scale(1)→scale(1.08)` over 20s) already used by the real Hero. Over the splash's ~1.35s visible window, scale only reaches ≈1.005 (0.5%) — comfortably under the 2% ceiling, with no new keyframes.
- **Native frame layout**: the entire, uncropped Hero photo (spec: "never crop important visual elements") is scaled to fit the canvas width or ~50% of canvas height (whichever is smaller), anchored near the top, over a heavily blurred/darkened full-bleed copy of itself for atmosphere. The (cropped) logo mark and a static "DISCOVER • EXPLORE • EXPERIENCE" tagline sit in the scrimmed space below — sized off the canvas's shorter side so both read at a consistent physical size in portrait or landscape.
- **Native splash background**: changed from cream (`#FBF8F3`) to navy (`#051427`, matching `tailwind.config.ts`'s `navy-900`) across `capacitor.config.ts` (3 fields), `android/.../colors.xml`'s `splashBackground`, and `LaunchScreen.storyboard`'s image-view background — the color that shows at any `CENTER_CROP` aspect-ratio edge, previously cream (which would have flashed pale against a now-dark photo splash).
- **PNG size**: the first-pass composite (true-color PNG) was ~1.3MB per density/orientation — 10+ copies in one APK. Switched to palette-quantized PNG (`sharp .png({ palette: true, quality: 90 })`) — still a valid, losslessly-decoded PNG, but ~300KB per file with no visible banding on the photo or the navy gradient scrim. The logo mark dropped from ~670KB to ~95KB the same way.

## Animation timeline (web overlay)

t=0 is the instant both the hero photo and the logo image fire their `onLoad` — not component mount — so the timeline never starts against an image that isn't actually painted yet.

| Element | Animation | Start | Duration | Easing |
|---|---|---|---|---|
| Backdrop + scrim | opacity 0→1 | 0ms | 550ms | `[0.16,1,0.3,1]` |
| Backdrop | Ken Burns (scale 1→1.08/20s) | 0ms | continuous, ~1.35s visible | `ease-out` |
| Logo | opacity 0→1, scale 0.96→1.00 | 0ms | 500ms | `[0.16,1,0.3,1]` |
| Tagline | opacity 0→0.85 | 650ms | 300ms | `[0.22,1,0.36,1]` |
| Hold | — | 950ms | 50ms | — |
| Exit (whole overlay) | opacity 1→0 | 1000ms | 350ms | `[0.16,1,0.3,1]` |

Total visible ≈1350ms — inside the requested 1.2–1.5s window.

**Reduced motion** (`useReducedMotion()`): fades still play in full; only transforms drop — the backdrop skips `animate-kenburns` (stays at `scale-100`), the logo skips its scale animation (stays at `scale-100`), both still fade in/out normally.

## Native ↔ web hand-off

`components/shared/native-splash-gate.tsx` (new) is a small context/hook pair, modeled on this codebase's own `search-overlay-provider.tsx` sibling-coordination pattern: `reportReady()` / `waitUntilReady(timeoutMs)`. `components/shared/splash-overlay.tsx` calls `reportReady()` the instant its own timeline begins (both images loaded); `components/shared/capacitor-bootstrap.tsx` now does `await waitUntilReady(1200); await SplashScreen.hide();` instead of hiding immediately on hydration. The 1200ms cap means a stalled or never-mounted overlay (any non-homepage cold-launch route) can never hang the native splash past that ceiling; `capacitor.config.ts`'s existing `launchShowDuration: 4000` remains the outermost safety net if this JS path doesn't run at all.

The overlay itself only ever shows once per app session (`sessionStorage` flag) and only when `window.Capacitor?.isNativePlatform?.()` is true — every normal web visitor renders `null` permanently, at zero cost.

## Platform differences

Both platforms share the identical composite-generation logic (`heroSplashComposite()`), so the only real difference is canvas shape: Android generates 10 density × orientation variants (matching its existing multi-density drawable convention) plus one fallback; iOS uses Apple's own simplified single-universal-image convention (one 2732×2732 square duplicated across the 1x/2x/3x `Contents.json` slots Xcode's template already expects).

## What this pass does not and cannot verify

No macOS/Xcode toolchain exists in this environment (confirmed repeatedly across this project's sessions) — every iOS "verification" above is config/XML correctness only, never an actual build, archive, or simulator run. Concretely, **not verified**: actual on-device flicker-freeness on either platform, actual 60fps, actual sub-2-second cold start on a real mid-range Android device, any real iOS runtime behavior at all, and Android 12+'s actual OS-level splash rendering on a physical device. The gating/timing *logic* was verified by direct code inspection (the 1200ms cap, the `onLoad`-gated readiness, the session-scoped one-time trigger), and the offline-caching *logic* is unchanged by this pass (once the homepage is cached via the existing service-worker rules, a later offline cold launch still serves the cached homepage rather than the native error fallback) — but neither was exercised on a device. A real-device install/smoke-test on both platforms is still worth doing before shipping this to users, same caveat as every prior native build in this project.

iOS's own project version (`ios/App/App.xcodeproj`) was not bumped in this pass — it still trails Android's versionCode/versionName from the last time iOS was actually built. Worth reconciling whenever iOS is next built.
